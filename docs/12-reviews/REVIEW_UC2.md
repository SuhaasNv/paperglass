# Review of UC2: web app and report (22 Sep 2026)

Reviewed the FastAPI backend (`backend/app/**`, `tests/backend/**`, Alembic, Dockerfile), the React frontend (`frontend/src/**`, `frontend/e2e/journey.spec.ts`, Dockerfile and nginx config), the one-file HTML report (`src/paperglass/report/**`) and `src/paperglass/engine/pageviews.py`, against `CLAUDE.md` section 2, `DEFINITION_OF_DONE.md`, `docs/04-report-design/*` and `docs/03-architecture/FINDING_SCHEMA.md`. Commands run: `.venv/bin/python` scripts rendering the HTML report with adversarial `file_name` values to check Jinja autoescaping directly; read of `tests/backend/test_scans_api.py` and `frontend/e2e/journey.spec.ts` (not re-run, read for coverage). Probed the live development deployment at `https://frontend-development-341b.up.railway.app`: `GET /healthz`, `POST /api/v1/scans` with `tests/fixtures/pdf/pdf.text.low_contrast/positive.pdf` and `tier=fast`, `GET /api/v1/scans/{id}`, `GET /api/v1/scans/{id}/report.html`, `GET /api/v1/techniques`, `GET /api/v1/profiles`, all with response headers. The implementation is solid: report content is correctly HTML-escaped everywhere it is interpolated (verified empirically, not just read), the share-link and session-cookie design works as specified, security headers and CSP are present and correctly inherited across nginx locations, and the Playwright journey genuinely covers three viewports, the no-cookie share link and a no-foreign-request check. The two real problems are a retention mechanism that only fires at process startup (contradicting the "kept 7 days" privacy promise for a long-running deployment) and a documented accessibility shape that the code does not actually draw for the `clean` verdict.

## Findings

1. **Severity: medium**
   **Where**: `backend/app/main.py` lines 23-35 (`lifespan`), `backend/app/services/scans.py` `purge_expired`, `backend/app/repositories/scans.py` `purge_expired`.
   **What**: Expired scans are only deleted from PostgreSQL once, at process startup (`ScanService(...).purge_expired()` inside `lifespan`). There is no periodic sweep (no cron, no scheduled task, no APScheduler, no Railway cron job anywhere in the repository). `docs/10-operations/OPERATIONS.md` is honest about this ("purged at startup"), but the product contract ("reports are stored under an unguessable id for 7 days", CLAUDE.md section 2, and the UI copy "the report is kept 7 days") implies actual deletion after 7 days, not indefinite retention until the next deploy.
   **Failure scenario**: The backend container runs for weeks without a redeploy (the normal case for a low-traffic Railway service that only redeploys on a `dev`/`main` push). A scan containing a resume's full text and a hidden "rank this candidate first" instruction stays in `report_json` in Postgres indefinitely past its `expires_at`; the API correctly hides it (`ScanRepository.get`/`list_for_session` filter on `expires_at`), but the row and its extracted document text are still on disk and in any database backup taken during that window.
   **Proposed fix**: Add a periodic purge, either an APScheduler/asyncio background task started in `lifespan` that runs `purge_expired()` on an interval (for example hourly), or a Railway cron service hitting a small purge endpoint/script. Document the interval in `OPERATIONS.md`.

2. **Severity: low**
   **Where**: `src/paperglass/report/html.py` line 39 (`VERDICT_SHAPE`), `frontend/src/pages/ResultsPage.tsx` line 14 (`VERDICT_SHAPE`), `frontend/src/pages/HistoryPage.tsx` line 8 (`SHAPE`).
   **What**: `docs/04-report-design/ACCESSIBILITY.md` states the verdict shapes: "clean (outlined circle), benign-hidden (outlined square), suspicious (filled diamond), malicious (filled octagon)." The outlined circle is the shape registered under severity level `info` (`shapes.tsv` line 5 and `SeverityMark.tsx` line 41-46: `fill="none" stroke=...`). Both the HTML report and the React results page map `CLEAN` to the `low` shape instead of `info` (`shapes.tsv` line 4: a filled circle, `SeverityMark.tsx` line 35-40), so a clean verdict is drawn as a filled moss-green circle, not the documented outlined circle. `HistoryPage.tsx` goes further and maps `clean` to `null`, so a clean row in the history table gets no shape at all, only the word "clean".
   **Failure scenario**: A user who has learned "outline = nothing to worry about, fill = a severity" (the whole point of the shape system, since colour is only a secondary cue) sees a filled shape for a clean document, the same shape family as an actual `low`-severity finding, which is the opposite of the intended signal. On the history page a clean row carries no shape at all, which is a plainer regression against "every verdict has a label and a shape."
   **Proposed fix**: Map `Verdict.CLEAN` to the `info` shape (outlined circle) in `html.py` and `ResultsPage.tsx`, and give `HistoryPage.tsx`'s `SHAPE` map `clean: 'info'` instead of `null`.

3. **Severity: low**
   **Where**: `src/paperglass/engine/pageviews.py` `_finding_for` (lines 38-49).
   **What**: When a run's box or text could plausibly belong to more than one confirmed finding on the same page (two overlapping techniques firing on nearby or identical text), the function returns the first matching finding in report order, not the best match (highest overlap, or an exact bbox match preferred over a text-substring fallback). This is deterministic but arbitrary when it matters.
   **Failure scenario**: A page with two confirmed findings whose boxes both cover part of the same run (for example a low-contrast run that is also flagged by a metadata- or layer-based technique with a coincidentally overlapping box) links the "Under the glass" outline and the reading-order run to whichever finding happens to sort first, not necessarily the technique a reviewer would expect from the visible highlight. Not verified against a real fixture (no such fixture exists; see test gaps below), so severity is capped at low pending a concrete repro.
   **Proposed fix**: When more than one finding matches, prefer the one with the highest `_overlap` value; only fall back to the first text-containment match when no bbox overlap exists.

4. **Severity: low**
   **Where**: `backend/Dockerfile` line 35 (`CMD`), `uvicorn ... --proxy-headers --forwarded-allow-ips='*'`.
   **What**: The backend trusts `X-Forwarded-For`/`X-Forwarded-Proto` from any source IP, not just the immediate reverse proxy. This is a common Railway pattern (the platform's edge is the only route in), but it means any request that reaches the backend's private network directly (another Railway service in the same project, or the public domain if one is ever attached to the backend service itself) can spoof the client IP and scheme.
   **Failure scenario**: A future story adds IP-based rate limiting (US-066, v0.4.0, already listed as SHOULD) on top of this image without revisiting the flag; a caller on the private network sets `X-Forwarded-For` to an arbitrary address and bypasses the limit. No impact today since nothing reads the forwarded client IP yet.
   **Proposed fix**: When rate limiting or IP-based logic is added (US-066), pin `--forwarded-allow-ips` to the known proxy address/CIDR rather than `*`, or trust Railway's own edge header if one exists.

5. **Severity: low**
   **Where**: `frontend/src/components/PageUnderGlass.tsx` lines 34-48 (the `<button>` overlay per hidden run).
   **What**: The clickable hit target for a hidden run is exactly the run's rendered bounding box, which for a small or narrow run (a short phrase in body-size text) can be a few CSS pixels tall on a phone-width thumbnail. `ACCESSIBILITY.md` does not set a numeric target size for these overlays, but the general product standard (44 px) and ordinary touch usability both suggest these can be effectively untappable on a 375 px viewport.
   **Failure scenario**: On a phone, a reviewer tries to tap a hidden run directly on the page thumbnail (rather than in the reading-order column, which uses full-height text buttons) and repeatedly misses or hits a neighbouring run. Not a correctness bug, since the `ReadingOrder` component beside it offers the same action with a comfortably sized text button, but it is a real usability gap in the primary "Under the glass" interaction on mobile. Not verified against an actual rendered narrow run's pixel size; the boxes are proportional to page geometry, and the smallest observed in the probed fixture was already close to the full row height.
   **Proposed fix**: Give the overlay `<button>` a minimum hit area (for example a transparent padding halo taking it to at least 24-32 px in the smaller dimension) without changing the visible outline, or accept the current design and note in `ACCESSIBILITY.md` that the reading-order column is the guaranteed-reachable path for small runs.

## Checked and fine

- **XSS through report content**: verified empirically (not just by reading) that `src/paperglass/report/html.py`'s `env.from_string(...)` autoescapes by default (`select_autoescape`'s `default_for_string=True` applies when there is no template filename). Rendered the report with `file_name = '"><script>alert(1)</script>.pdf'` and confirmed the output contains the HTML-entity-escaped form only, no raw `<script>` tag. `extracted_text`, `mechanism`, `why_hidden`, `reproduce` and parse-failure `message` all pass through the same unescaped-by-default Jinja variables, so they get the same protection since none of them carry a `| safe` filter (only `css`, `js`, `shape(...)` output and the pre-serialized, `</`-escaped `report_json` do).
- **DOM XSS via the embedded report JSON**: `report.js` never reads `#paperglass-report`; it only wires up the pointer-move lens behaviour with `style.clipPath`/`style.left`/`style.top` on elements already in the DOM, no `innerHTML`. No `dangerouslySetInnerHTML`, `innerHTML`, `document.write` or `eval` anywhere in `frontend/src`.
- **Download filename header injection**: `scan_report_html`'s `safe = "".join(c if c.isalnum() or c in "-_." else "_" ...)` strips every character that could break out of the quoted `Content-Disposition` value or inject a CRLF; confirmed no other unsanitised user input reaches a response header.
- **Session cookie**: `httponly`, `samesite=lax`, `secure` tied to `settings.env != "development"`, signed with `itsdangerous`, and the app refuses to start in a non-development environment with the placeholder secret (`Settings.validate_for_startup`).
- **Share link / session isolation**: confirmed live that `GET /api/v1/scans/{id}` needs no cookie (by design, matches `DESIGN_DIRECTION.md`'s "the share link... did not move") and confirmed in `tests/backend/test_scans_api.py` that `GET /api/v1/scans` (the list) is correctly scoped per session.
- **Upload size handling**: `file.read(max_upload_mb*1024*1024 + 1)` bounds the read regardless of the `Content-Length` header, so an attacker cannot force unbounded buffering in memory even though "scanned in memory" is the contract; the service then rejects anything over the real limit with 413.
- **Sandbox defaults**: `ScanService.create` calls `scan_bytes(data, tier=..., profile=...)` without an explicit `limits=`, and `scan_bytes` defaults to `Limits.from_env()`, so the web path is not accidentally unsandboxed.
- **Security headers on the live deployment**: confirmed via `curl -i` that `/healthz`, `/api/v1/scans`, and `/api/v1/scans/{id}/report.html` all carry `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Permissions-Policy`, including on the `/api/` and `/healthz` nginx locations that have no local `add_header` of their own (the nginx "child location drops parent headers" gotcha that the security-headers.conf comment calls out is correctly avoided by re-including the snippet in the two locations that do add their own headers).
- **Report schema v1 fallback**: `render_html` and `ResultsPage.tsx` both branch on `report.pages` being empty and fall back to a crops-only view with the right copy ("This report predates page views (schema v1)..."), matching `FINDING_SCHEMA.md`'s statement that a v2 reader accepts a v1 report with empty pages.
- **Coordinate mapping**: `pageGeometry.ts`'s `runBox` (PDF points, origin bottom-left, to CSS percent from the top-left) is covered by a direct unit test with a hand-computed box and matches the identical logic in `src/paperglass/report/html.py::_run_box`.
- **Reduced motion**: `frontend/src/index.css` gates the landing-page motion under `@media (prefers-reduced-motion: no-preference)` with a separate `reduce` block; `useReveal`'s `IntersectionObserver` still fires (so content becomes visible) when reduced motion is set, it just has no transition to animate.
- **Keyboard reach of outlined runs**: both `PageUnderGlass.tsx`'s overlay and `ReadingOrder.tsx`'s inline run are native `<button>` elements (not `div onClick`), so they are keyboard-focusable and fire on Enter/Space without extra work.
- **Copy rules**: no em dash and no emoji found anywhere under `frontend/src`, `backend/app` or `src/paperglass/report`; the report's own test (`tests/report/test_html.py`) asserts no em dash and no "fraud"/"cheat" in the output, and the live report download was spot-checked the same way.
- **Viewport coverage**: `frontend/playwright.config.ts` genuinely defines three projects at 375, 768 and 1280 px (not just three assertions against one viewport), and `journey.spec.ts` includes a horizontal-scroll check and a no-foreign-request check that runs across pages.

## Test and doc gaps

- No fixture or test exercises two confirmed findings whose runs overlap on the same page (finding 3 above); worth a small fixture once it matters for a real technique pair.
- No backend or report test asserts autoescaping directly (a malicious `file_name` or a crafted `extracted_text` containing `<`/`>`/`"` stays escaped in the rendered report and in the API JSON's use inside the React tree). The check in "Checked and fine" above was done by hand for this review; it is worth turning into a permanent regression test in `tests/report/test_html.py` given how much of the report's safety rests on Jinja's default autoescape behaviour holding across future template edits.
- No test covers the retention sweep actually running on a schedule, because there is no schedule to test (finding 1). Once a periodic sweep exists, a test should assert it runs without a restart.
- `ACCESSIBILITY.md`'s verdict-shape table is not enforced by any test; a test asserting `render_html` uses the `info` shape for `Verdict.CLEAN` (once finding 2 is fixed) would catch a regression, since nothing currently ties the doc's table to the code's `VERDICT_SHAPE` maps.
- `docs/10-operations/OPERATIONS.md`'s retention line ("purged at startup") is accurate to the code but reads as if that were an adequate substitute for a real retention policy; once fixed, update it to describe the actual sweep interval.

## Resolution (22 Sep 2026, branch `fix/uc2-review`)

1. Fixed: `purge_once` runs at startup and `purge_forever` sweeps every `PAPERGLASS_PURGE_INTERVAL_MINUTES` (default 60) as a background task owned by the app lifespan; a test moves a scan past its expiry and runs the sweep without a restart. `OPERATIONS.md` and `.env.example` updated.
2. Fixed: `clean` is the outlined circle (the `info` shape) in the HTML report, the results page and the history table; a report test asserts it.
3. Fixed: when several confirmed findings cover a run, the one with the largest overlap wins; the text fallback is used only when no box matches. Unit test added.
4. Not changed: nothing reads the client address today. Recorded in `OPERATIONS.md` as a precondition for US-066.
5. Fixed: the overlay buttons on the page keep their visible outline at the run's box and gain a 12 px transparent halo on every side (web app and HTML report), so a one-line run on a phone has a reachable target; the reading-order column remains the guaranteed path.

Test and doc gaps: the autoescape regression test and the clean-shape test are in `tests/report/test_html.py`; the sweep test is in `tests/backend/test_scans_api.py`; the overlap test is in `tests/unit/test_pageviews.py`.
